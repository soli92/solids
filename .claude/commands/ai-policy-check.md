# /ai-policy-check

Check **detective** §ai_policy (Layer-2). Verifica che i repo cliente con
`suppress_ai_traces: true` non contengano attribution AI ne' ID kanban factory
nella loro history git.

**Layer-2, non Layer-1**: non sostituisce gli hook git locali (preventivi), li affianca.
Detective, non preventivo. Mai auto-fix sulla history: segnala, la riscrittura e' decisione umana.

**Guardia di scope (invariante)**: il repo della factory stessa non viene MAI scansionato,
nemmeno se passato esplicitamente con `--repos`. Qui l'attribution AI nei commit del
framework e' DOVUTA, non vietata. Il tentativo produce un rifiuto esplicito, non uno skip
silenzioso.

La guardia confronta il **repo git** (toplevel), non il path: un submodule in
`code_repos/` sta dentro la cartella della factory ma e' un altro repo, ed e' proprio il
repo cliente da scansionare. Una sottocartella non-repo (`wiki/`) e' la factory e viene
rifiutata; un path inesistente e' `unscanned: repo_not_found`, non un rifiuto.

---

## Utilizzo

```
/ai-policy-check                        # scope da ai_policy_check.scope[] in factory.config.yaml
/ai-policy-check --repos=../client-x    # repo espliciti (relativi alla factory root o assoluti)
/ai-policy-check --repos=../a,../b      # piu' repo separati da virgola
/ai-policy-check --root=../derivata     # opera su un'altra factory: path relativi e scope[] sono suoi
/ai-policy-check --strict               # gate bloccante: exit 1 se ci sono violations (pre-push)
/ai-policy-check --from-hook            # output compatto (per embed in hook o altri tool)
```

**`--strict`** trasforma il check in un gate bloccante (exit 1 se ci sono violations).
Usare **solo** in contesti bloccanti come pre-push o dev-handoff. **Non usare** in
session-close o altri contesti non bloccanti: il check advisory (exit 0) e' quello giusto.

> **Submodule con husky o un altro hook manager.** Se il submodule ridefinisce `core.hooksPath`,
> git ignora `.git/hooks` e gli hook §ai_policy sono inerti: `install_submodule_hooks.py` lo
> rileva e avvisa senza installare (`tools/vcs/README-submodule.md`). Per quei submodule
> `--strict` prima del push e' l'unico controllo meccanico. Con violazioni: report completo in
> chat, STOP prima di push o handoff, il fix e' umano (si riformula il messaggio; `sm-commit.sh`
> toglie attribution e ID kanban).

## Come funziona

Per ogni repo target:
1. **Finestra commit**: `git log @{u}..HEAD` (commit locali avanti sull'upstream).
   Se non c'e' upstream → fallback agli ultimi 20 commit (ragione dichiarata nel report).
2. **Staged diff**: `git diff --cached`.
3. Per ogni commit: **messaggio** e **righe aggiunte** nel diff.

Cerca:
- **Attribution AI**: righe che contengono `co-authored-by`, `generated with`,
  `generated by`, `claude`, `anthropic` (case-insensitive).
- **ID kanban factory**: ID nella forma `TSK-NNN`, `US-NNN`, `EP-NNN` (questa factory)
  o `XX-TSK-NNN`, `XXX-US-NNN` (factory derivate multi-namespace).

**Operazione read-only**: zero push, zero fetch, zero modifiche. Solo comandi git di lettura.

## Output partition

```
OK clean (N):
  <repo>    commits_checked: M

!! violations (N):
  <repo>    commits_checked: M
    [a1b2c3d] [message] -> Co-Authored-By: ...

? unscanned (N):
  <repo>    reason: not_a_git_repo
```

- `clean` — nessuna traccia trovata.
- `violations` — attribution AI o ID kanban factory trovati.
- `unscanned` — errore per-repo (repo non trovato, non e' un git repo, timeout git).
  Errore per-repo = `unscanned` con reason, mai crash dell'intero check.

## Configurazione

Abilitare il blocco in `factory.config.yaml`:

```yaml
ai_policy_check:
  enabled: false          # opt-in; a false la factory e' identica a v2.43
  scope:
    - path: ../client-repo-a   # relativo alla factory root
    - path: /abs/path/repo-b   # o path assoluto
```

Lo scope e' indipendente dal `vcs.mode` dell'entry (`submodule`, `sibling`, `external`).
A scope vuoto lo strumento dice che non ha nulla da scansionare e termina con exit 0:
**non e' un errore**.
