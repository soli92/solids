# Controllo §ai_policy sullo spec e commit nel repo di test

Riferimento della skill `cypress-generation-protocol`. Ambito: elenco dei riferimenti vietati negli
spec, comando di scansione e regole di commit per submodule e override. Si legge prima di dichiarare
lo spec pulito (verifica Fase 3, Fase 4 punti 2 e 3) e prima di ogni commit nel repo di test.

Gli spec entrano nel repo di un cliente (`code_repos/` o un clone che ne fa le veci): valgono le
regole di CLAUDE.md §ai_policy. Prima di ogni commit, sui file aggiunti o modificati (`git diff` e
file nuovi), **0 corrispondenze** a:

| Categoria | Cosa cercare |
|---|---|
| ID kanban | `\b(?:[A-Z]{2,4}-)?(?:TSK\|US\|EP)-\d+\b` (pattern di `tools/vcs/ai_policy.py`, fonte unica) |
| Gap e domande | `\bG-[A-Z0-9]+(?:-[A-Z0-9]+)*-\d+\b`, `\bQ-[A-Z]+-\d+\b` |
| ADR, regole | `\bADR-\d+\b`, `\bR\.\d+\b`, `\bINV-` |
| Nomi di agenti e di pipeline | `cypress-test-analyst`, `cypress-test-reviewer`, `qa-dev`, `code_quality`, `generation-plan`, `golden rule` |
| AI e attribution | `claude`, `anthropic`, `generated with`, `generated by`, `co-authored-by`, `AI`/`LLM` riferiti all'origine del codice |
| Gergo di processo | wiki/log, wiki/gaps, tavola rotonda, gate, travaso, milestone |

Ammessi: ticket del cliente (work item del suo tracker), RFC/WCAG/CVE, issue pubbliche open source.
Comando di riferimento (da eseguire con Bash, esito 0 righe):

```bash
git -C "<test_path>" diff -U0 HEAD | grep -E '^\+[^+]' | grep -n -i -E \
  '(TSK|US|EP)-[0-9]+|G-[A-Z0-9-]+-[0-9]+|ADR-[0-9]+|claude|anthropic|co-authored|cypress-(test-analyst|test-reviewer)|qa-dev|code_quality|golden rule'
```

Per i file non ancora tracciati, aggiungerli prima con `git add -N <path>` o scansionarli con `grep` diretto.
Un riscontro si corregge riscrivendo il commento come spiegazione del *perché*; mai si «maschera»
il testo. Il messaggio di commit è soggetto alle stesse regole e non contiene `Co-Authored-By`.

## Commit

- **Repo di test come submodule o clone nel working tree della factory** (fonte `submodule` del
  resolver): `tools/vcs/sm-commit.sh "messaggio" <test_path>`. Il messaggio viene filtrato da
  `tools/vcs/ai_policy.py` e, se alterato, va confermato (`--yes` per l'uso non interattivo). Se il
  repo di test è un submodule con puntatore da aggiornare: `python3 tools/vcs/sm_commit.py
  --coordinated "<messaggio>" --target <nome-submodule>` (`--no-pointer` se il branch non è ancora
  mergiato nella sua base). Messaggio neutro, in stile umano, senza ID né firme. Niente `git commit`
  diretto.
- **Override su clone personale** (fonte `override`): un clone fuori dalla factory non è coperto dal
  commit coordinato. Il controllo equivalente è quello sopra, eseguito sul clone, **dichiarato** nel
  `generation-plan.md` (comando, data, esito 0 righe) e ripetuto sul messaggio di commit. Il commit lo
  fa l'operatore con il proprio autore; la pipeline non lo firma e non lo pubblica.
- Nessuna operazione VCS distruttiva senza gate umano; nessun `--no-verify`.
- Controllo detective sulla history: `python3 tools/vcs/ai-policy-scan.py --strict --repos=<test_path>`
  prima del push, solo se il repo è tra quelli dichiarati in `ai_policy_check.scope[]`. Il repo della
  factory non si scansiona mai.
